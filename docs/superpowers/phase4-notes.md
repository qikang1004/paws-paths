# 阶段 4 笔记：运营后台

阶段 3 把举报与复核的服务端做完了，但运营侧只有 API 没有界面 —— 复核得靠 curl。
这一阶段做的是一个独立的 Web 后台（`admin/`），以及它需要的那条**密码登录**链。

## 一、为什么是独立 Web + 密码登录

小程序不适合当运营工具：复核要看原图、要读长正文、要连续处理几十条，手机屏幕
与小程序的导航模型都在跟这件事作对。而运营账号也不该绑微信身份 —— 那意味着
每个运营都得先是这个小程序的用户，离职时要撤的东西还多一样。

密码登录因此不是「多一种登录方式」，是**另一类主体**：小程序用户走 openid，
运营走用户名密码，两条路的凭据、限流维度与失败语义全不同。挤进一个端点迟早
让某一条的限流套错，所以 `admin-login` 与 `wx-login` 是两个端点。

## 二、合成 openid：让运营账号能不存在于微信

`users.openid` 有 `NOT NULL UNIQUE`，而纯运营账号压根没有微信身份。做法是
`admin:<用户名>` —— 真 openid 是 28 位左右的 base64-ish 串，**不含冒号**，
所以这个前缀不可能与之相撞。

替代方案是把那列改成可空，但那要改一条既有的 NOT NULL 约束，而 openid 为空的行
会让每个读 openid 的地方都多一次判空（`msgSecCheck` 那条路径尤其）。前缀占位
把影响面收在一处。

## 三、两列都必须可空

```sql
ALTER TABLE users ADD COLUMN IF NOT EXISTS username TEXT;
ALTER TABLE users ADD COLUMN IF NOT EXISTS password_hash TEXT;
CREATE UNIQUE INDEX IF NOT EXISTS users_username_idx
  ON users (username) WHERE username IS NOT NULL;
```

`NOT NULL` 会让迁移在有数据的旧库上直接失败，而给所有用户加密码等于开一条
全新的、不该存在的攻击面。部分索引写成 `WHERE username IS NOT NULL` 不是为了
绕开什么 —— Postgres 的 UNIQUE 本来就允许多个 NULL —— 而是把意图讲明白：
「没有用户名」不是一种需要互斥的值。它同时也是登录查询的索引。

## 四、防枚举：两种失败必须一字不差

「用户名不存在」与「密码错误」收敛成同一个 401、同一句文案。这件事有三个落点，
缺一个就漏：

1. `AuthService.badCredentials()` 是**唯一**的构造点 —— 两处分别 new 迟早分叉；
2. 限流键控用**请求里的用户名**而不是解析后的 userId：用户名不存在时也必须计数，
   否则「猜用户名」这一步完全不受限；
3. 前端不按 code 分支写自己的文案（`admin/README.md` 里记着这条）——
   服务端收敛了，前端拆开等于白做。

刻意**没做**时序对齐（找不到用户时假验一次密码）：scrypt 单次 50–100ms，而限流
已经把速率压到一小时 10 次，那个量级下时序差异问不出东西。真要防时序得让整条
路径恒定时间，那是另一个工程。

## 五、限流两条都要

`admin-login` 同时按用户名与 IP 计数，一小时各 10 次，哪条先满都是 429。
只按用户名：换用户名就绕过。只按 IP：分布式爆破换 IP 就绕过。

**副作用要在上线前核**：同一出口 IP 的多个运营共享那 10 次配额，办公网 NAT
后面人多时可能不够。这条记进了 `RELEASE_CHECKLIST.md`。

守卫拿不到用户名时**直接放行不计数** —— 那种请求接下来必然是 422，把配额留给
真正的爆破尝试。

## 六、CLI 是唯一的加人入口

没有注册端点，这是有意的：运营账号不该能从公网创建，而「注册入口忘了删」是
一类真实存在的事故。代价是加人要登服务器。

密码从 **stdin** 读而不是命令行参数 —— 参数会进 shell history 与 `ps` 输出。

同一个用户名再跑一次是改密码与改角色，所以它同时是重置密码工具与降权工具。
再单开一条重置路径只会多一处会分叉的 SQL。

那条 upsert 用单条 CTE 而不是「先 SELECT 再决定 INSERT/UPDATE」：后者在两个人
同时建同一个用户名时会双双走到 INSERT，其中一个撞唯一索引崩掉。

## 七、把那条 SQL 从 CLI 里搬出来

`scripts/create-admin.ts` 从 argv 取参、从 stdin 读密码、跑完 `process.exit` ——
**测试碰不到它**。而它内联的那条 upsert 是整条运营登录链上唯一会写库的语句，
写错的后果是「建出一个登不进去的账号」或「悄悄改掉了别人的密码」。

搬到 `src/auth/admin-account.ts`，只接受一个能 `query` 的东西（`Pool` 与
`PoolClient` 都满足），于是集成测试可以在事务里跑它再回滚。这一步之后才有可能
写出「CLI 建出来的账号真能登进去」这条断言 —— 那是本阶段最要紧的一条，
而它跨了 upsert、部分唯一索引、`findCredentialByUsername` 与 scrypt 校验四处。

## 八、前端的几个取向

**不引路由库、不引 UI 框架。** 两个视图、七个组件，引进来的包比省下的代码多。
等审计日志页进来（那时真的需要「地址栏表达位置」）再引。

**判据是业务码不是 HTTP 状态。** 服务端的包络是 `{ code, message, data }`，
HTTP 200 也可能带非 0 的码。与小程序侧同一套约定。

**非包络响应要有确定形状。** 反代挂了会回一段 HTML，直接 `.json()` 会抛一个
与业务无关的 SyntaxError，界面上表现成「操作失败：Unexpected token <」——
对运营毫无意义。

**存坏了的会话按「没登录」处理，不抛。** 它在 `useState` 的初始化里跑，
抛出去就是白屏，而白屏没有自救路径。

**复核成功后重拉当前页**，不是把那条从本地数组里摘掉：队列在动（其他运营也在判、
新举报还在进），摘一条会让这一页少显示一条，而下一条本该从后面补上来。

**UGC 一律走文本插值，绝不用 `dangerouslySetInnerHTML`。** 令牌就在
`localStorage` 里，而被举报的正文是攻击者可控的内容。

## 九、`/uploads` 漏配：一个只有真起服务才看得见的 bug

工单里的 `imageUrls` 是服务端拼的相对路径（`/uploads/:ownerId/:name`），而
`vite.config.ts` 起初只代理了 `/api` —— 那些 `<img>` 请求全打在 dev server 上
拿 404，**后台里一张图都看不见**。

单元测试看不出来：它们用的是 `fetch` 替身，压根不发真请求。所以补了
`test/vite-config.spec.ts`，断言**导入进来的配置对象**而不是文件文本 ——
文本正则会被注释里的同名字符串骗过去（那个坑在 miniprogram 那侧踩过五次，
阶段 3 笔记第五节那张表记着）。删掉 `/uploads` 那条规则重跑，5 例里 3 例转红。

`/uploads` 不能 rewrite：服务端那条路由本身就带这个前缀，去掉会 404。
这与 `/api` 相反（服务端路由上没有 `/api` 那一段）。

## 十、待审图片运营看不到 —— 前端解决不了

待审图落私有档，`UploadsService.fetch` 里只对 `parsed.ownerId` 开放，而 `<img>`
压根不会带 Authorization 头 —— 运营连自己的身份都递不过去。

界面上的处置是**显式说明**而不是留碎图：缩略图画成虚线占位，大图给一段能照着
排错的话（待审图只有作者能取；已过审的图若也这样，查反向代理）。碎图图标看起来
与「后台坏了」一模一样，而这两件事的处置完全不同。

真要让运营看待审图，得服务端单开一条路径。动手前先想清楚：那条路径会让运营能取
**任意**私有图，不只是被举报的那张。

## 十一、审核流水页：为什么它与工单页不能合并

两张表的**职责**不同（spec §4.4 的原话，Global Constraint 25 也钉着）：
`moderation_tasks` 是待办队列，会被更新、处理完就不在列表里；`audit_log` 是只追加的
合规记录。所以两个列表下发的字段刻意相反：

| | 工单列表 | 流水列表 |
| --- | --- | --- |
| 被举报内容原文 | 有（运营要看内容才判得了） | **没有** |
| 举报人是谁 | **不下发**（会招来报复） | 不适用 |
| 动作与操作人 | 不适用 | 有（合规审查要问这个） |

流水不带原文的理由是它**要比它记录的目标活得久**：动态被作者删了，那条
「谁撤下了它」的记录仍然必须查得到。带原文会让这一半在删除后变成空字段，
诱导客户端去判空。

### `LEFT JOIN` 而不是 `JOIN`

取操作人显示名那一句用的是 `LEFT JOIN users`。写成内连接会让两类流水
**从合规视图里消失**，而它们恰恰是最需要留痕的那些：

- 机审的流水 `actor_id` 是 NULL —— 那不是人做的动作；
- 账号注销后那个 id 指向不存在的行 —— `actor_id` 不挂外键（流水必须比主体活得久），
  所以这是正常状态，不是数据损坏。

界面上这三种情况分开显示（「系统（机审）」/「已注销（id）」/ 名字），
混成一个「-」会让读流水的人分不清「机器做的」与「这个人注销了」。

### `ORDER BY created_at DESC, id DESC`

`id DESC` 不是装饰：单条 CTE 里写两条流水时 `created_at` 完全相同
（`now()` 在一条语句里是常量），只按时间排会出不确定的顺序 ——
那会让分页在页边界上漏行或重复。`listByTarget` 那边早就这么写了，这里同源。

### 仓储上是 `list` 而不是给 `listByTarget` 加参数

`listByTarget` 是「这条内容的历史」：调用点在复核流程里、结果全量返回
（一条内容的流水撑不到要分页）。`list` 是运营后台的合规视图：必须分页、
要带操作人显示名。混成一个方法会让前者也背上 JOIN 与分页参数。

接口面仍然只有**读与追加** —— 加这个方法没有动 Global Constraint 25，
那条契约测试（禁止 update/delete/remove/clear）照旧绿。

## 十二、验证到哪一步了

**本环境没有 Postgres 也没有 Redis**（docker daemon 不可用，`which postgres`
`which redis-server` 都空），所以所有带库断言仍是 skip 状态。

已有的证据：

| 层 | 手段 | 覆盖 |
| --- | --- | --- |
| 密码哈希 | 单测 9 例 | 含时序安全与成本参数向后兼容 |
| CORS 解析 | 单测 11 例 | 通配符、非 https、路径、尾斜杠全拦 |
| 登录端点 | 单测 11 例 | 双维限流键、防枚举、令牌不带角色 |
| upsert 参数 | 单测 8 例（新） | 位置绑定、uuid 生成、单条语句 |
| 角色白名单 | 单测 3 例（新） | 库里是乱值时返回 null |
| 前端 | vitest 81 例 | 含包络判据、UGC 不解析、代理配置、流水页三种操作人 |

仍然只能靠真库/真 Redis 证的（都已写成 skip 的集成套件或走查步骤）：

- `admin-account.integration.spec.ts` 8 例 —— 建号、改密码、降权、
  「建出来的账号真能登进去」、小程序用户取不到凭据、大小写敏感
- `phase4-walkthrough.mjs` —— 密码登录这条链的端到端，含流水端点的形状与
  「四个写入动词全 404」。阶段 3 那份走查拿运营令牌走的是 `wx-login` + 假微信开关，
  **一行都不碰 `admin-login`**
- 流水列表的 `LEFT JOIN` 在真库上的行为（机审那条 `actor_id` 为 NULL 的记录
  不该被内连接吞掉）—— 内存实现证不了这个，它压根没有 JOIN
- 双维限流在真 Redis 上的 INCR/EXPIRE（走查里那段默认跳过 ——
  跑一次会把该 IP 的配额烧满一小时）
- CORS 的预检请求（`OPTIONS`）与浏览器里的实际跨域调用
